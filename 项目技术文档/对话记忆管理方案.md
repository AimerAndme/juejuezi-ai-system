# 对话记忆管理方案

## 一、核心思想

采用 **"批次化摘要 + 滑动窗口"** 的混合方案，通过以下策略降低 Token 消耗：

1. **批次化摘要**：维护当前批次消息，每 10-20 条消息生成一次摘要
2. **智能触发**：达到最小批次（10 条）且 token 超过阈值（1500），或达到最大批次（20 条）时生成摘要
3. **摘要列表**：维护最近 6 条摘要，满 6 条时丢弃最早的一条
4. **当前批次**：chat:memory:{conversationId} 存储当前批次消息（10-20 条）
5. **自动清空**：生成摘要后，当前批次消息清空，新消息重新累积
6. **Redis 滑动窗口**：Redis 存储时自动裁剪，保持最多 20 条消息，避免内存占用过大
7. **批次清空标记**：摘要提取导致的缓存清空会添加标记，避免触发不必要的缓存重建

## 三、工作流程

### 1. 请求处理流程（before 方法）

```java
public ChatClientRequest before(ChatClientRequest chatClientRequest, AdvisorChain advisorChain) {
    String conversationId = getConversationId(chatClientRequest.context(), defaultConversationId);

    // 步骤1：获取当前批次消息
    List<Message> memoryMessages = chatMemory.get(conversationId);
    List<Message> processedMessages = new ArrayList<>();

    if (memoryMessages == null || memoryMessages.size() == 0) {
        log.info("会话id：{}，未查询到短期记忆", conversationId);
    }
    log.info("会话id：{}，查询到短期记忆{}条", conversationId, memoryMessages.size());

    // 步骤2：判断是否启用摘要功能
    if (enableSummary) {
        // 步骤3：获取摘要列表
        List<String> summaryList = null;
        if (chatMemory instanceof RedisChatMemory) {
            RedisChatMemory redisChatMemory = (RedisChatMemory) chatMemory;
            summaryList = redisChatMemory.getSummaryList(conversationId);
        }

        // 步骤4：组装上下文（摘要列表 + 当前批次消息）
        if (summaryList != null && !summaryList.isEmpty()) {
            String combinedSummary = String.join("\n\n", summaryList);
            Message summaryMessage = new SystemMessage("历史对话摘要：\n" + combinedSummary);
            processedMessages.add(summaryMessage);
            log.info("会话id：{}，使用{}条摘要", conversationId, summaryList.size());
        }

        // 步骤5：添加当前批次消息
        processedMessages.addAll(memoryMessages);
        log.info("会话id：{}，上下文已组装为：{}条摘要 + {}条当前批次消息",
            conversationId, summaryList != null ? summaryList.size() : 0, memoryMessages.size());
    } else {
        // 步骤6：未启用摘要，直接使用当前批次消息
        processedMessages = memoryMessages;
    }

    // 步骤7：添加当前请求的指令消息
    processedMessages.addAll(chatClientRequest.prompt().getInstructions());

    // 步骤8：构建处理后的请求
    ChatClientRequest processedChatClientRequest = chatClientRequest.mutate()
        .prompt(chatClientRequest.prompt().mutate().messages(processedMessages).build())
        .build();

    // 步骤9：保存用户消息到当前批次
    UserMessage userMessage = processedChatClientRequest.prompt().getUserMessage();
    chatMemory.add(conversationId, userMessage);

    return processedChatClientRequest;
}
```

### 2. 响应处理流程（after 方法）

```java
public ChatClientResponse after(ChatClientResponse chatClientResponse, AdvisorChain advisorChain) {
    // 步骤1：提取助手回复消息
    List<AssistantMessage> assistantMessages = new ArrayList();
    if (chatClientResponse.chatResponse() != null) {
        assistantMessages = chatClientResponse.chatResponse().getResults().stream()
            .map(g -> g.getOutput())
            .toList();
    }

    // 步骤2：获取对话ID
    String conversationId = getConversationId(chatClientResponse.context(), defaultConversationId);

    // 步骤3：保存助手回复到当前批次
    chatMemory.add(conversationId, assistantMessages);

    // 步骤4：判断是否启用摘要功能
    if (enableSummary && chatMemory instanceof RedisChatMemory) {
        RedisChatMemory redisChatMemory = (RedisChatMemory) chatMemory;

        // 步骤5：获取当前批次消息
        List<Message> currentBatch = redisChatMemory.get(conversationId);

        // 步骤6：计算当前批次的token数
        int batchTokens = calculateTokens(currentBatch);

        // 步骤7：判断是否需要生成摘要
        boolean shouldGenerateSummary = false;

        if (currentBatch.size() >= batchSizeMax) {
            // 达到最大批次，强制生成
            shouldGenerateSummary = true;
            log.info("会话id：{}，批次已达到最大限制（{}条），强制生成摘要",
                conversationId, currentBatch.size());
        } else if (currentBatch.size() >= batchSizeMin && batchTokens >= batchTokenThreshold) {
            // 达到最小批次且token超过阈值
            shouldGenerateSummary = true;
            log.info("会话id：{}，批次已达到token阈值（{} tokens, {}条），生成摘要",
                conversationId, batchTokens, currentBatch.size());
        }

        // 步骤8：生成摘要
        if (shouldGenerateSummary) {
            String summary = generateSummary(currentBatch);

            if (summary != null) {
                // 步骤9：添加到摘要列表
                redisChatMemory.addSummaryToList(conversationId, summary, maxSummaries);
                // 步骤10：清空当前批次
                redisChatMemory.clearCurrentBatch(conversationId);
                log.info("会话id：{}，摘要已生成并保存，当前批次已清空", conversationId);
            } else {
                // 步骤11：摘要生成失败，记录警告
                log.warn("会话id：{}，摘要生成失败", conversationId);
            }
        }
    }

    return chatClientResponse;
}
```

### 3. 摘要生成流程

```java
private String generateSummary(List<Message> messages) {
    try {
        // 步骤1：将消息列表转换为文本
        String conversationText = messages.stream()
            .map(msg -> {
                String role = msg.getMessageType().name();
                String content = msg.getText();
                return String.format("[%s]: %s", role, content);
            })
            .collect(Collectors.joining("\n"));

        // 步骤2：构建摘要生成提示词
        String prompt = String.format(
            "请将以下对话历史压缩成简洁的摘要，保留关键信息、重要决策和上下文。摘要应该清晰、简洁，便于后续对话理解：\n\n%s\n\n摘要：",
            conversationText
        );

        // 步骤3：调用大模型生成摘要
        return summaryChatClient.prompt()
            .user(prompt)
            .call()
            .content();
    } catch (Exception e) {
        // 步骤4：异常处理，返回null
        log.error("摘要生成失败，将回退到纯滑动窗口模式。错误信息：{}", e.getMessage());
        return null;
    }
}
```

### 4. Token 计算流程

```java
private int calculateTokens(List<Message> messages) {
    return messages.stream()
        .mapToInt(msg -> {
            String content = msg.getText();
            // 简单估算：中文约1.5 tokens/字
            return (int) (content.length() * 1.5);
        })
        .sum();
}
```

### 5. 摘要列表管理流程

```java
public void addSummaryToList(String conversationId, String newSummary, int maxSummaries) {
    String key = SUMMARY_LIST_KEY_PREFIX + conversationId;

    // 步骤1：获取现有摘要列表
    List<String> summaries = getSummaryList(conversationId);

    // 步骤2：添加新摘要
    summaries.add(newSummary);

    // 步骤3：如果超过上限，直接丢弃最旧的摘要
    while (summaries.size() > maxSummaries) {
        summaries.remove(0);
        log.info("会话id：{}，已丢弃最旧的摘要", conversationId);
    }

    // 步骤4：保存到Redis
    redisTemplate.delete(key);
    redisTemplate.opsForList().rightPushAll(key, summaries);
    redisTemplate.expire(key, 7, TimeUnit.DAYS);

    log.info("会话id：{}，当前摘要数量：{}", conversationId, summaries.size());
}

public List<String> getSummaryList(String conversationId) {
    String key = SUMMARY_LIST_KEY_PREFIX + conversationId;
    Long size = redisTemplate.opsForList().size(key);

    // 如果列表为空，返回空列表
    if (size == null || size == 0) {
        return new ArrayList<>();
    }

    // 从Redis获取摘要列表
    List<Object> objects = redisTemplate.opsForList().range(key, 0, -1);
    return objects.stream()
        .map(Object::toString)
        .collect(Collectors.toList());
}
```

### 6. 当前批次管理流程

```java
public void clearCurrentBatch(String conversationId) {
    String key = getRedisKey(conversationId);
    redisTemplate.delete(key);

    // 添加标记，记录这是摘要提取导致的清空
    String clearedKey = BATCH_CLEARED_PREFIX + conversationId;
    redisTemplate.opsForValue().set(clearedKey, "true", 1, TimeUnit.HOURS); // 1小时过期

    log.info("会话id：{}，当前批次已清空", conversationId);
}
```

## 五、成本分析

### 场景 1：消息较短（平均 50 tokens/条）

```

       → 达到20条，强制生成摘要
批次2：20条 × 50 tokens = 1000 tokens（未达到阈值）
       → 达到20条，强制生成摘要
批次3：20条 × 50 tokens = 1000 tokens（未达到阈值）
       → 达到20条，强制生成摘要

摘要生成成本：3次 × 500 tokens = 1500 tokens
上下文Token消耗：3条摘要 × 200 tokens + 20条 × 50 tokens = 1600 tokens
```

## 六、优势

1. **智能触发**：根据消息长度动态调整摘要生成时机
2. **避免极端**：有上下限（10-20 条），避免批次过大或过小
3. **成本可控**：token 阈值 1500，避免批次过大导致 token 消耗过多
4. **逻辑清晰**：批次化管理，每 10-20 条生成一次摘要
5. **摘要列表固定**：最多 6 条，不会无限增长
6. **对话连续性**：当前批次消息保留，保证最近上下文完整
7. **内存控制**：Redis 滑动窗口保持 20 条消息，避免内存占用过大
8. **缓存优化**：摘要提取后避免不必要的缓存重建，提高性能
9. **自动过期**：批次清空标记 1 小时过期，避免长期占用 Redis 空间

## 七、劣势

1. **信息丢失**：批次消息完全依赖摘要，可能丢失细节
2. **依赖 LLM 能力**：摘要质量完全依赖 LLM 的生成能力
3. **额外成本**：需要调用 LLM 生成摘要，增加 Token 消耗
4. **时效性问题**：摘要生成后，如果对话继续发展，旧摘要可能不再准确
5. **Redis 依赖**：依赖 Redis 存储摘要列表，存在数据丢失风险

## 八、适用场景

**适合：**

- 对话主题相对独立，早期信息对后续影响不大
- 对话轮数较多（>30 轮），Token 消耗成为主要问题
- 消息长度较长，批次化方案能显著节省成本
- 对上下文完整性要求不高的场景

**不适合：**

- 需要长期上下文的复杂对话
- 对信息完整性要求极高的场景
- 对话轮数较少（<20 轮），摘要生成成本高于节省的 Token
- 消息长度较短，纯滑动窗口更优

## 九、未来优化方向

1. **智能摘要触发**：基于话题变化、重要程度等智能判断是否需要生成摘要
2. **摘要质量评估**：使用另一个 LLM 验证摘要质量，确保关键信息不丢失
3. **分层摘要**：实现不同粒度的摘要（详细、中等、简略），根据需求选择
4. **摘要缓存优化**：优化 Redis 存储结构，提高查询效率
5. **降级策略**：摘要生成失败时，自动回退到纯滑动窗口模式

**方案总结：** 这是一个基于 token 阈值的智能批次化摘要方案，通过 10-20 条的批次大小和 1500 的 token 阈值，实现了智能的摘要生成时机控制。

**核心优势：**

- **智能触发**：根据消息长度动态调整摘要生成时机
- **内存优化**：Redis 滑动窗口保持 20 条消息，避免内存占用过大
- **性能提升**：摘要提取后避免不必要的缓存重建，提高系统响应速度
- **成本可控**：在消息较长时能显著节省 token 消耗，在消息较短时也能保持合理性能
- **逻辑清晰**：批次化管理，每 10-20 条生成一次摘要，摘要列表固定 6 条
- **对话连续性**：当前批次消息保留，保证最近上下文完整

**技术亮点：**

- **批次清空标记**：通过 Redis 标记区分缓存过期和摘要提取导致的缓存清空
- **缓存重建优化**：摘要提取后直接返回空列表，避免重复处理已生成摘要的消息
- **自动过期机制**：批次清空标记 1 小时过期，避免长期占用 Redis 空间

**适用场景：**

- 对话轮数较多（>30 轮），Token 消耗成为主要问题
- 消息长度较长，批次化方案能显著节省成本
- 对话主题相对独立，早期信息对后续影响不大
- 对上下文完整性要求不高的场景

这是一个实用且易于维护的解决方案，通过混合使用摘要和当前批次消息，在保持对话连贯性的同时，有效降低了 Token 消耗。
