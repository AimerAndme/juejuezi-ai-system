## 1. 概述

### 1.1 背景

在 RAG（检索增强生成）系统中，文档分片是影响检索质量的关键因素。不合理的分片会导致：

- **检索质量下降**：不相关的文档分数反而更高
- **召回率低**：相关文档被分割到多个分片中，无法完整检索
- **精确率低**：分片包含过多无关信息，干扰检索结果
- **语义不完整**：在句子或段落中间分割，破坏语义完整性

### 1.2 优化目标

- 提高检索质量（Precision@K、Recall@K、MRR）
- 保持语义完整性
- 优化分片大小分布
- 支持多种分片策略
- 提供灵活的配置选项

### 1.3 技术栈

- **Spring AI**: TokenTextSplitter
- **Apache Tika**: 文档内容提取
- **自定义实现**: 语义分片、重叠窗口

## 2. 问题分析

### 2.1 TokenTextSplitter 默认配置问题

```java
// 原始代码
TokenTextSplitter tokenTextSplitter = new TokenTextSplitter();
List<Document> split = tokenTextSplitter.split(new Document(textContent));
```

**默认参数**：

- `chunkSize`: 500 tokens
- `overlapSize`: 100 tokens
- `keepSeparator`: false
- `trimWhitespace`: true

**存在的问题**：

| 问题            | 影响               | 原因                     |
| --------------- | ------------------ | ------------------------ |
| 分片大小固定    | 不适应不同文档类型 | 无法根据文档类型调整     |
| 重叠比例固定    | 召回率不稳定       | 20% 重叠可能不够         |
| 不保留分隔符    | 语义边界不清晰     | 无法识别段落、句子边界   |
| 无最小/最大限制 | 分片大小不均匀     | 可能出现过小或过大的分片 |

### 2.2 检索质量不高的原因

#### 原因 1：分片大小不合适

```
场景 1：分片太大
- 问题：包含过多无关信息
- 影响：检索结果不相关
- 示例：1000 tokens 的分片，查询"传感器"，返回包含"传感器"的长篇技术文档

场景 2：分片太小
- 问题：缺少上下文
- 影响：检索结果不完整
- 示例：100 tokens 的分片，查询"传感器安装步骤"，返回分散的多个分片
```

#### 原因 2：语义边界被破坏

```
示例：在句子中间分割
原文："传感器应安装在通风良好的位置，避免潮湿和高温环境。"
分片 1："传感器应安装在通风良好的位置，"
分片 2："避免潮湿和高温环境。"

问题：
- 分片 1 缺少完整信息
- 分片 2 缺少主语
- 语义不完整，影响检索
```

#### 原因 3：重叠不足

```
示例：关键信息在分片边界
分片 1："...智能矿山系统包括传感器网络、数据采集..."
分片 2："...数据采集系统和监控平台三个部分。"

查询："智能矿山系统组成部分"
问题：
- 分片 1 包含部分信息
- 分片 2 包含部分信息
- 缺少重叠，检索时可能只返回其中一个分片
```

## 3. 优化方案

### 3.1 总体架构

```
文档上传
    ↓
内容提取 (Apache Tika)
    ↓
分片策略选择
    ├─ Token 分片
    ├─ 语义分片
    └─ 固定字符数分片
    ↓
分片处理
    ├─ 段落级分割
    ├─ 句子级分割
    ├─ 词级分割
    └─ 重叠窗口
    ↓
质量过滤
    ├─ 最小分片过滤
    ├─ 最大分片限制
    └─ 空白字符修剪
    ↓
向量化存储
```

### 3.2 核心改进

#### 改进 1：可配置的分片参数

```yaml
file:
  parsing:
    chunk-size: 500 # 分片大小（tokens）
    overlap-size: 100 # 分片重叠大小（tokens）
    min-chunk-size: 100 # 最小分片大小（tokens）
    max-chunk-size: 1000 # 最大分片大小（tokens）
    split-strategy: token # 分片策略
    keep-separator: true # 是否保留分隔符
    trim-whitespace: true # 是否修剪空白字符
```

#### 改进 2：三种分片策略

| 策略         | 实现方式        | 优点                     | 缺点           | 适用场景           |
| ------------ | --------------- | ------------------------ | -------------- | ------------------ |
| **token**    | 基于 Token 数量 | 简单高效，适合大多数场景 | 不考虑语义边界 | 通用文档、新闻文章 |
| **semantic** | 基于语义边界    | 保持语义完整性           | 计算复杂度高   | 技术文档、法律文档 |
| **fixed**    | 固定字符数      | 最简单                   | 可能破坏语义   | 简单描述、日志     |

#### 改进 3：智能语义分片

```java
// 段落级分割
String[] paragraphs = text.split("\n\n+");

// 句子级分割（中英文标点）
String[] sentences = paragraph.split(
    "(?<=[。！？；])|(?<=[.!?;])\\s+"
);

// 词级分割
String[] words = sentence.split("\\s+");

// 重叠窗口
chunks = addOverlap(chunks, overlapSize);
```

#### 改进 4：质量监控

```java
log.info("分片配置: 策略={}, 分片大小={}, 重叠大小={}",
         splitStrategy, chunkSize, overlapSize);
log.info("文档分割成功，共 {} 个分片", chunks.size());
log.info("分片大小统计: 平均={} 字符, 最小={} 字符, 最大={} 字符",
         avgSize, minSize, maxSize);
```

## 5. 分片策略详解

### 5.1 Token 分片策略

#### 5.1.1 实现原理

```java
TokenTextSplitter tokenTextSplitter = new TokenTextSplitter(
    chunkSize,      // 分片大小
    overlapSize,    // 重叠大小
    minChunkSize,   // 最小分片
    maxChunkSize,   // 最大分片
    keepSeparator   // 是否保留分隔符
);
List<Document> split = tokenTextSplitter.split(new Document(textContent));
```

#### 5.1.2 工作流程

```
原始文本
    ↓
Token 化
    ↓
按 chunkSize 分割
    ↓
添加 overlapSize 重叠
    ↓
过滤过小/过大的分片
    ↓
返回分片列表
```

#### 5.1.3 优缺点

**优点**：

- 简单高效
- 适合大多数场景
- 分片大小均匀

**缺点**：

- 不考虑语义边界
- 可能在句子中间分割
- 不适合需要保持语义完整性的文档

#### 5.1.4 适用场景

- 通用文档
- 新闻文章
- 博客文章
- 产品描述

### 5.2 语义分片策略

#### 5.2.1 实现原理

```java
private List<String> semanticSplit(String text) {
    // 1. 按段落分割
    String[] paragraphs = text.split("\n\n+");

    // 2. 按句子分割
    String[] sentences = paragraph.split(
        "(?<=[。！？；])|(?<=[.!?;])\\s+"
    );

    // 3. 按词分割
    String[] words = sentence.split("\\s+");

    // 4. 添加重叠窗口
    chunks = addOverlap(chunks, overlapSize);

    // 5. 过滤过小的分片
    chunks = chunks.stream()
        .filter(chunk -> chunk.length() >= minChunkSize)
        .toList();

    return chunks;
}
```

#### 5.2.2 工作流程

```
原始文本
    ↓
段落级分割
    ↓
句子级分割
    ↓
词级分割（如果句子过长）
    ↓
添加重叠窗口
    ↓
质量过滤
    ↓
返回分片列表
```

#### 5.2.3 分层分割逻辑

```
第一层：段落分割
  ├─ 空行分隔
  └─ 保持段落完整性

第二层：句子分割
  ├─ 中文标点：。！？；，、：
  ├─ 英文标点：.!?;:,
  └─ 保持句子完整性

第三层：词分割
  ├─ 空格分隔
  └─ 保持单词完整性
```

#### 5.2.4 重叠窗口实现

```java
private List<String> addOverlap(List<String> chunks, int overlapSize) {
    List<String> chunksWithOverlap = new ArrayList<>();

    for (int i = 0; i < chunks.size(); i++) {
        StringBuilder chunkWithOverlap = new StringBuilder();

        // 添加前一个分片的结尾
        if (i > 0) {
            String prevChunk = chunks.get(i - 1);
            String prevOverlap = getLastNChars(prevChunk, overlapSize);
            chunkWithOverlap.append(prevOverlap).append("\n\n");
        }

        // 添加当前分片
        chunkWithOverlap.append(chunks.get(i));

        // 添加下一个分片的开头
        if (i < chunks.size() - 1) {
            String nextChunk = chunks.get(i + 1);
            String nextOverlap = getFirstNChars(nextChunk, overlapSize);
            chunkWithOverlap.append("\n\n").append(nextOverlap);
        }

        chunksWithOverlap.add(chunkWithOverlap.toString());
    }

    return chunksWithOverlap;
}
```

#### 5.2.5 优缺点

**优点**：

- 保持语义完整性
- 在句子、段落边界分割
- 适合技术文档、法律文档

**缺点**：

- 计算复杂度高
- 分片大小不均匀
- 处理时间较长

#### 5.2.6 适用场景

- 技术文档
- 法律文档
- 学术论文
- 操作手册

### 5.3 固定字符数分片策略

#### 5.3.1 实现原理

```java
private List<String> splitTextIntoChunks(String text, int chunkSize) {
    List<String> chunks = new ArrayList<>();
    for (int i = 0; i < text.length(); i += chunkSize) {
        String chunk = text.substring(i, Math.min(i + chunkSize, text.length()));
        chunks.add(chunk);
    }
    return chunks;
}
```

#### 5.3.2 工作流程

```
原始文本
    ↓
按固定字符数分割
    ↓
返回分片列表
```

#### 5.3.3 优缺点

**优点**：

- 最简单
- 处理速度最快
- 分片大小完全均匀

**缺点**：

- 不考虑语义边界
- 可能在单词中间分割
- 不适合需要保持语义完整性的文档

#### 5.3.4 适用场景

- 简单描述
- 日志文件
- 数据记录
- 不需要语义的文本

## 8. 故障排查

### 8.1 常见问题

#### 问题 1：分片数量过多

**现象**：

```
文档分割成功，共 500 个分片
分片大小统计: 平均=25 字符, 最小=10 字符, 最大=50 字符
```

**原因**：

- 分片大小设置过小
- 最小分片过滤未生效

**解决方案**：

```yaml
chunk-size: 800 # 增大分片大小
min-chunk-size: 200 # 设置最小分片过滤
```

#### 问题 2：分片数量过少

**现象**：

```
文档分割成功，共 3 个分片
分片大小统计: 平均=4000 字符, 最小=3000 字符, 最大=5000 字符
```

**原因**：

- 分片大小设置过大
- 最大分片限制未生效

**解决方案**：

```yaml
chunk-size: 500 # 减小分片大小
max-chunk-size: 1000 # 设置最大分片限制
```

#### 问题 3：检索质量不高

**现象**：

```
Precision@5: 0.45
Recall@5: 0.38
MRR: 0.52
```

**原因**：

- 分片大小不合适
- 重叠不足
- 分片策略不匹配

**解决方案**：

```yaml
# 方案 1：调整分片大小
chunk-size: 800 # 增大分片大小

# 方案 2：增加重叠
overlap-size: 200 # 增加重叠大小

# 方案 3：切换策略
```

#### 问题 4：处理时间过长

**现象**：


**原因**：

- 使用语义分片策略
- 文档过大
- 缓冲区太小

**解决方案**：

```yaml

# 方案 2：增加缓冲区

```

#### 问题 5：内存不足

**现象**：

```
java.lang.OutOfMemoryError: Java heap space
```

**原因**：

- 文档过大
- 缓冲区设置过大
- 内存阈值设置过高

**解决方案**：

```yaml
# 方案 1：降低内存阈值

# 方案 2：减小缓冲区
```

## 13. 项目深入优化方向

### 13.1 代码质量优化

#### 13.1.1 代码规范与注释

- **问题**：部分核心类缺少方法注释和参数说明
- **优化方向**：
  - 为所有公共方法添加 JavaDoc 注释
  - 统一代码风格，使用 CheckStyle 或 SpotBugs 进行静态检查
  - 添加业务逻辑注释，特别是复杂的算法实现
- **预期收益**：提升代码可维护性，降低新人上手难度

#### 13.1.2 异常处理体系

- **问题**：异常处理不够细致，缺少自定义异常体系
- **优化方向**：
  - 设计分层异常体系（BusinessException、SystemException、ValidationException）
  - 实现全局异常处理器，统一错误响应格式
  - 添加异常链追踪，便于问题定位
- **预期收益**：提升系统稳定性，便于问题排查

#### 13.1.3 配置管理优化

- **问题**：配置文件中存在硬编码路径和敏感信息
- **优化方向**：
  - 使用 @ConfigurationProperties 管理配置
  - 敏感信息使用环境变量或配置中心（如 Nacos、Apollo）
  - 实现配置热更新，无需重启服务
- **预期收益**：提升安全性，便于多环境部署

### 13.2 性能优化

#### 13.2.1 向量化服务优化

- **问题**：向量化服务未实现批量处理，每次请求处理数量有限
- **优化方向**：
  - 实现批量向量化接口，支持一次处理多个文本
  - 添加向量化结果缓存，减少重复计算
  - 使用连接池优化 HTTP 请求性能
- **预期收益**：向量化速度提升 3-5 倍，降低 API 调用成本

#### 13.2.2 检索性能优化

- **问题**：混合检索未充分利用缓存和索引
- **优化方向**：
  - 为常用查询添加 Redis 缓存
  - 优化 Elasticsearch 索引配置（分片数、副本数）
  - 实现查询结果预加载
  - 使用 Elasticsearch 的 query cache 和 request cache
- **预期收益**：检索响应时间从 500ms 降低至 100ms 以内

#### 13.2.3 数据库连接池优化

- **问题**：HikariCP 配置较为保守，未充分利用数据库性能
- **优化方向**：
  - 根据实际负载调整连接池大小
  - 添加连接池监控指标
  - 实现读写分离，主库写、从库读
- **预期收益**：提升并发处理能力，降低数据库压力

#### 13.2.4 流式响应优化

- **问题**：SSE 流式响应存在延迟，用户体验不够流畅
- **优化方向**：
  - 优化 LLM 调用参数，减少首字延迟
  - 实现响应缓冲，减少网络传输次数
  - 添加心跳机制，防止连接中断
- **预期收益**：首字响应时间从 500ms 降低至 200ms

### 13.3 安全性增强

#### 13.3.1 权限控制

- **问题**：缺少细粒度权限控制，所有用户访问相同数据
- **优化方向**：
  - 实现 RBAC 权限模型
  - 在检索时添加 orgTag 权限过滤
  - 实现数据隔离，不同用户只能访问自己的数据
- **预期收益**：提升数据安全性，满足企业级应用需求

#### 13.3.2 API 安全

- **问题**：API 接口缺少认证和授权机制
- **优化方向**：
  - 集成 Spring Security 或 Sa-Token
  - 实现 JWT 认证
  - 添加接口限流（使用 Redis + Lua 脚本）
  - 实现 API 签名验证
- **预期收益**：防止未授权访问，保护系统安全

#### 13.3.3 文件上传安全

- **问题**：文件上传缺少安全校验，存在安全风险
